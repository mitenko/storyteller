# M3: what the work found

**Status:** M3 is code-complete and open as [PR #9](https://github.com/mitenko/storyteller/pull/9).
**Date:** 2026-09-14
**Scope:** findings from specifying, planning and building the voice badge and
picker — the things that were not true, were not implementable, or were not being
tested, and what was done about each.

Nothing here is a request for work. It is the record of what the milestone turned
up, so the decisions can be argued with rather than inherited.

---

## 1. Three claims in the spec were wrong, and reading the code found them

The spec was written before the code was read closely. Three of its load-bearing
statements did not survive contact.

### 1.1 The labels the whole design rests on were not in the app

The trio is chosen by contrasting voices on gender and age. `VoiceDto` declared
`voice_id` and `name` **and nothing else** — no labels were being parsed, so there
was nothing to contrast on. The spec described a computation over data the app did
not have.

Fixed by Task 1, which exists only to get the labels in. Measured against the live
account the same day, the labels are real and complete: every one of the 21 voices
carries `gender`, `age` and `use_case`.

### 1.2 The playback ruling was not implementable

The spec said opening the picker "leaves playback alone." The app has **one**
`PagePlayer`. An audition has to come out of it, so a page reading underneath an
audition is two voices at once — not a design choice, a defect.

Corrected in the spec (`658b411`) rather than quietly planned around: the picker
stops playback, and the reader's position survives because its ViewModel sits on the
back stack. Worth noting *when* this was caught — during planning, by writing out
the data flow, not during implementation.

### 1.3 Re-synthesis needed no new pipeline API at all

The spec treated re-preparing the page as the expensive, unsolved part. It is
neither. `ReadingPipeline.retry()` already re-prepares from the in-memory parse
without a vision call, and `openStored` sets that parse too — so it works for
library pages as well as freshly photographed ones.

The saving is not the code avoided. It is that no new state machine was introduced
into the one component in this app where concurrency has already gone wrong twice.

## 2. Two tests were vacuous, and one was written to avoid being vacuous

This is the finding worth the most attention, because it recurred **inside a test
written specifically to avoid it**.

### 2.1 A seeded random made an overwrite test prove nothing

`assign overwrites a voice already chosen` did:

```kotlin
val first = r.voiceFor("cogsley").getOrThrow()
r.assign("cogsley", "m-old").getOrThrow()
assertEquals("m-old", r.voiceFor("cogsley").getOrThrow())
```

`Random(42)` over a three-voice pool happened to draw **`m-old`** — the very voice
the test then assigned. The assertion passed without anything having changed.

It only surfaced because the test carried a guard asserting `first != "m-old"`. The
guard was written on the assumption it would never fire. It fired on the first run.

Fixed by targeting whichever voice the roll did *not* produce, which holds whatever
the seed does. **The general lesson: a test whose subject is a change must compute
its target from the observed starting state, not name it in advance.**

### 2.2 A StateFlow handed a test the stale value and it fell straight through

The milestone's headline test — that changing one voice re-buys only that
character's lines — was written using turbine:

```kotlin
p.retry()
p.state.test {
    while (awaitItem() !is PipelineState.Ready) { }
    cancelAndIgnoreRemainingEvents()
}
assertEquals(afterFirstRead + 2, audio.synthesisCount)
```

A `StateFlow` **replays its current value to every new subscriber.** The pipeline was
already `Ready` from the first read, so `awaitItem()` returned that stale `Ready`
immediately, the loop exited before `retry()` had bought anything, and the assertion
ran too early.

It failed — 4 where 6 was expected — which looked at first like the economic claim
being false. It was the test being wrong. Driving the scheduler with
`advanceUntilIdle()` instead makes the measurement real: **4 clips after the first
read, 6 after the voice change, 1 vision call throughout.**

### 2.3 Why this keeps happening

M5 shipped a vacuous headline test (`opening a stored page never calls the page
reader`, asserted with no `advanceUntilIdle()`). M3's headline test was written in
direct knowledge of that failure and fell into a variant of it anyway.

The common shape is not "forgot to advance the dispatcher". It is **asserting that a
counter stayed at zero**, or that nothing happened, in a world where nothing has run
yet. Such an assertion is satisfied by the code working, by the code failing, and by
the test never getting as far as the code.

The defence that actually worked here was not vigilance. It was:

- asserting on a counter that must **move** (`4 → 6`), not one that must stay put
- pairing each claim with a positive one that would fail if nothing ran
  (`assertTrue(p.state.value is PipelineState.Ready)`)
- writing a guard against the test's own vacuity, and **believing it when it fired**

The first is worth adopting as a habit for this repo: where a test's claim is "X did
not happen", find the neighbouring quantity that must have happened and assert on
that too.

## 3. Smaller findings

**The narrator was already a character.** `prepare()` resolves
`unit.voiceKey ?: NARRATOR`, so narration has a real row in the voice map. Its badge
therefore works like any other rather than being a dead label — the feature was
larger than the spec claimed, for free.

**`navArgument` is not in the compose package.** Navigation 2.9 puts it at
`androidx.navigation.navArgument`. A one-line finding, recorded only because the
plan asserted the wrong import and an executor would have hit it.

**`StoredPageEntity`'s kdoc still carries a claim known to be false.** It says the
stored-page id is "the same key `parsed_page` uses — so they agree by construction".
They never did: the parse cache keys on `sha256(image.bytes + PAGE_VISION_MODEL.id)`.
This was corrected in the M5 *spec* (`a73fa8f`) but the entity comment was missed.
Out of scope for M3 and left alone; it is a one-line fix whenever that file is next
touched.

## 4. What M3 leaves open

### 4.1 No spend cap — and the bar just got lower

Nothing in this app limits spending. Until M3, every cost required **photographing a
page**, which is a slow, deliberate act. M3 is the first feature that spends money on
a **tap**. A child changing a voice on a ten-line page buys ten clips; doing it
repeatedly buys them repeatedly.

This is the largest gap in the app and M3 widened it.

Feature #20 (M14 in the backlog) bounds it cheaply rather than solving it: cap the
page at three distinct voices, and a character has at most three targets, so once
each has spoken a line that line's clip is cached and flipping between them costs
nothing. Unbounded becomes a small constant. A real cap after that can be smaller.

### 4.2 The device check has not run for two milestones running

M5's Task 6 never ran. M3's Task 7 Step 6 has not run either — no Pixel on the USB
bus, only the Clover terminal, which is not ours to touch.

Seven manual steps are unverified, and three of them are claims **no unit test can
reach**:

- that the three offered voices are *audibly* different — the whole point of scoring
  contrast on gender and age is a judgement about what a four-year-old can hear, and
  nobody has heard it
- that the page visibly stops when the picker opens
- that re-reading produces no new diagnostic bundle

Add to that M10A.6: nobody has yet heard whether "MM" actually hums. The app now has
three separate claims about **sound** that have only ever been verified as code.

The APK is built and waiting at `app/build/outputs/apk/debug/app-debug.apk`.

### 4.3 The pool is more lopsided than the design assumed

Measured 2026-09-14 across the account's 21 voices: **13 male, 7 female, 1 neutral**;
ages **13 middle_aged, 7 young, 1 old**. Only two voices are marked
`characters_animation`.

The practical consequence is that random assignment across six characters routinely
produces three or four middle-aged American men. This is the measurement behind
feature #20, and it is a stronger argument for a capped palette than the "a child can
only follow three voices" claim it was written to support: even three *random* voices
are likely to be two men of the same age.

## 5. Decisions taken during planning that were not in the spec

Recorded because they were judgement calls, and each is cheap to reverse:

| decision | why | where it lives |
|---|---|---|
| Re-preparation is `pipeline.retry()` | No new state machine in the component concurrency has already bitten twice | `VoicePickerViewModel.confirm` |
| The page restarts from the top after a change | The child changed the voice in order to hear it | same |
| Contrast is gender 2, age 1, character-voice 1 | Deliberately crude, entirely inside one pure function | `chooseTrio` |
| Ties break on id | So a character sees the same pair twice running | same |
| The badge is tappable before the line's audio is ready | The wait is exactly when a child fiddles | `LineRow` |
| The audition is the character's **own** shortest line | Makes the current voice's clip already cached — the first card costs nothing | `VoicePickerViewModel.load` |
| `MIGRATION_6_7` drops `voice_list` rather than converting it | Converting means inventing the labels that then decide what a child is offered | `StorytellerDatabase.kt` |

The last one is the only one with a real cost: everyone refetches the voice list once
on next launch. `character_voice` is untouched, so **no assigned voice is lost** —
that half has its own migration test, because getting it the wrong way round would
silently re-randomise every character in the app.
